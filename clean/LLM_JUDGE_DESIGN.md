# LLM 裁判实验设计（草稿，2026-10-26）

**目的：** 补上论文动机和证据之间最大的缺口。到目前为止，所有比较都由真实回报生成，只证明了"算法不需要奖励幅度"，没有证明"没有奖励公式时也能学好"。

**要回答的三个问题：**
1. 换成真实的 LLM 裁判后，pair 相比"oracle 比较"损失多少？
2. 在同一个裁判下，两两比较（listwise 排名）、逐条打分、rubric 打分三种奖励来源，哪个训练出的策略在**隐藏的金标准**上更好？
3. 当手写奖励不完整时（漏掉了说明里的某些要求），用自然语言说明 + 裁判比较，能否学到手写奖励学不到的行为？

---

## 1. 比较方案：检查点 × 一次 listwise 排名

沿用预算实验的结论：在少数时间点上把全部配对比完，比每步只比一两对好得多（NOTES 4.12）。实现方式：

- 每组 K=8 条轨迹从同一初始状态出发。
- 每 L 步设一个检查点。在检查点 t，把还活着的轨迹"从 t 起的后续"各写成一段文字摘要，**一次调用**让裁判排序，允许并列（分层），由此得到全部 28 对比较，含平局。
- 窗口内的动作共用检查点的优势（`broadcast_window`）。critic 版本（pcrit_res）用同样的比较训练。
- **位置偏差：** 每次调用随机打乱呈现顺序，并记录顺序。是否需要"正反两次排序"（成本翻倍），由第 3 节的校准结果决定。
- **结构化输出：** 用 `output_config.format` 约束输出为 `{"tiers": [["C"], ["A","F"], ["B"], ...]}`，从好到差，同层即平局。
- **一个代价上的事实：** 一次 listwise 调用给出全部 28 对。逐条打分则需要 8 次调用（每条一次，才是真正的独立打分）。所以比较本身就比打分便宜约 8 倍调用，这一点可以写进论文。

**风险：** L=50 的检查点间隔没有验证过（只验证过 L=10）。第 0 阶段先用 oracle 免费验证。

## 2. 任务

### T1：LunarLander-NL（主任务，接已有结果）

- **裁判看到的说明：** "让着陆器平稳、直立地降落在两旗之间，少用燃料，不要坠毁。"不给任何权重或公式。
- **后缀摘要：** 每 25 步一帧的原始量（位置、速度、角度、两腿是否触地），加上最终事件（着陆 / 坠毁 / 超时）和主副引擎点火次数。**不包含奖励项本身**，避免把奖励"预先算好"喂给裁判。附录里再做一个"摘要信息量"消融。
- **金标准：** 环境原始回报（隐藏）+ 着陆成功率。
- **为什么选它：** oracle 比较下 pair 的表现已经知道（1M 步约 250，2M 步 262），可以干净地量出"LLM 裁判噪声"造成的损失。
- **规模：** 1M 步/运行，约 420 组、2,900 个检查点。

### T2：快递网格世界（新建，最能支撑"手写奖励不完整"）

- **环境：** 9×9 网格，每组随机布局（同组同 seed）。元素包括起点、取件点、送达点、岩浆（踩到立即失败）、花坛（可以踩，但说明里要求有合理绕路时不要踩）。时间上限 80 步。
- **裁判看到的说明：** "取件并送达；绝不踩岩浆；有合理的绕路时不要踩花坛；尽量快。"
- **后缀摘要：** 访问的格子序列，以及事件（第几步踩了花坛、取件、送达、岩浆）。
- **金标准（隐藏）：** 送达 +100，岩浆 −100，每步 −2，每次踩花坛 −15。
- **两个手写奖励基线：** naive（送达 +1、岩浆 −1）；"常见设计"（再加每步 −0.01）。两者都漏掉了花坛，这模拟设计者没想到或难以量化的要求。
- **预期：** 手写奖励学到"快但踩花坛"；裁判比较学到"绕开花坛"。在金标准上分出差别。
- **规模：** 300k 步/运行，约 750 组、4,500 个检查点（L=10，回合短）。
- **局限：** 这是人为构造的玩具任务，审稿人会这么说。它的作用是受控验证。真实 LLM agent 任务列为后续。

### 考虑过但不选

- **用 LLM 当策略的文本 agent 任务（ALFWorld、TextWorld 等）：** 需要 GPU 训练 LLM 策略，超出本机能力。可以作为后续扩展。
- **MuJoCo + 视觉裁判：** 要渲染帧，token 成本高约 10 倍。RL-VLM-F（2024）已经做过"VLM 偏好 + 奖励模型"，本工作的差异点不在这里。

## 3. 方法与对照

| 方法 | 信号 | 裁判调用/检查点 | 作用 |
|---|---|---|---|
| **pair + LLM 排名**（本文） | listwise 分层排名 → 两两比较 | 1 | 主方法 |
| **pcrit_res + LLM 排名** | 同上，加比较训练的 critic | 1 | 次要；预算实验显示低预算下它更脆弱 |
| GRPO + LLM 逐条打分 | 每条后缀独立打 0–10 分，按 t 做 z-score | 8 | "打分 vs 比较"的核心对照 |
| GRPO + LLM rubric 打分 | 按 3–4 条 rubric 分项打分再求和 | 8 | 更强的打分基线（文献：Rubrics as Rewards） |
| pair + oracle 比较 | 金标准生成的比较（同检查点方案） | 0 | 上界：裁判噪声造成的损失 |
| PPO + 金标准奖励 | 标量 | 0 | 参照 |
| PPO + 手写奖励（仅 T2） | naive / 常见设计 | 0 | "手写奖励有偏"的对照 |

- **两项控制：** 所有裁判方法用同一个模型、同一份任务说明、同一个检查点方案。
- **裁判设置**（是否思考、effort）在校准阶段定下，之后写进预注册文件，不再改。
- **随机性：** 2026-10-21 起 API 不再接受 temperature 参数，裁判本身有随机性。校准阶段会测重复一致率；训练中如果遇到完全相同的请求，复用缓存的结果。

## 4. 裁判模型与成本

### 4.1 价格

来源：claude-api 参考，缓存日期 2026-10-06。

| 模型 | 输入 $/百万 token | 输出 $/百万 token |
|---|---|---|
| Claude Haiku 5.5 | 0.10 | 0.50 |
| Claude Sonnet 5.5 | 2.00 | 10.00 |
| Claude Opus 5.5 | 4.00 | 20.00 |

Batch API 打五折，但结果异步返回（最长 24 小时），**只能用于校准，不能用于训练循环**。说明文字约 450 token，低于缓存的最小前缀，所以提示缓存基本省不了钱。

### 4.2 估算

假设：
- 说明约 450 token；每条后缀摘要约 60 token。
- listwise 输出约 40 token（不开思考）或约 300 token（low effort 思考）。
- 逐条打分输出约 10 token 或约 200 token。

每种方法 10 个种子的总成本：

| 方法（10 个种子） | T1 Haiku | T1 Sonnet | T2 Haiku | T2 Sonnet |
|---|---|---|---|---|
| pair 排名 | $3–7 | $66–142 | $5–11 | $102–219 |
| pcrit_res 排名 | $3–7 | $66–142 | $5–11 | $102–219 |
| 逐条打分 | $13–35 | $261–705 | $20–54 | $403–1,087 |
| rubric 打分 | $21–47 | $425–938 | $33–72 | $655–1,447 |
| **合计** | **$41–96** | **$818–1,927** | **$63–149** | **$1,262–2,971** |

区间的两端分别对应"不开思考"和"low effort 思考"。token 数是估计值，可能偏差 ±50%，试跑后会用实测数重算。

### 4.3 选项（需要你决定）

| 方案 | 内容 | 估计总成本 | 说明 |
|---|---|---|---|
| **A（建议）** | 全部方法用 Haiku 5.5，10 个种子；另在 T1 上用 Sonnet 5.5 跑 pair + 逐条打分，5 个种子，作为"裁判强弱"一个维度 | 约 $300–700（含校准） | 弱裁判是对"比较比打分容易"更严格的检验；强裁判那一维回答"结论是否依赖裁判强弱" |
| B | 只用 Haiku 5.5 | 约 $110–250 | 最便宜，但少了裁判强弱这一维 |
| C | 全部用 Sonnet 5.5 | 约 $2,100–4,900 | 结论不会因"裁判太弱"被质疑，但贵 10–20 倍 |

还需要你提供或确认：
- **API 账户与预算上限：** 本机目前没有任何 API 凭据（`ANTHROPIC_API_KEY` 未设置，也没有 `ant` CLI）。代码只从环境变量读取凭据，不会写进仓库。
- **数据范围：** 发给 API 的只有模拟环境生成的轨迹摘要，不含任何客户数据或个人信息。

## 5. 阶段与 go/no-go

| 阶段 | 内容 | API 成本 | 时间 |
|---|---|---|---|
| **0**（免费） | (a) oracle 比较下验证 L=50 的检查点方案：LunarLander，10 个种子，判据为保留率 ≥ 0.9，否则改用 L=25，调用量翻倍。(b) 写后缀摘要器、T2 环境、裁判客户端（并发限流、重试、全量记录每个请求和响应、相同请求缓存、每次运行的花费上限）。(c) 用 PPO + 金标准确认 T2 可学，手写奖励确实学成"踩花坛"。 | $0 | 1–2 天 |
| **1** 校准 | 从不同训练阶段的策略里抽 600 个检查点组。listwise 每组正反两种顺序各问两次；逐条打分每条问两次。测：与金标准的比较准确率（按 \|Δ\| 分段）、位置偏差、重复一致率、平局率、打分的 Spearman 相关和"分数挤在一起"的比例。同时比较"不开思考"和"low effort"。**go 判据（事先写）：** 差距明显的比较（\|z\| > 1）准确率 ≥ 85%，否则先改摘要或换裁判。 | Haiku 约 $1，Sonnet 约 $20（Batch） | 半天 |
| **2** 试跑 | 每种方法 1 个调参种子，实测调用量、token 和花费，修正 4.2 的估算，再定最终预算 | 约为正式预算的 10% | 半天 |
| **3** 正式 | 预注册后跑 10 个种子；裁判方法同时并发的运行数限制在约 6 个，避免触发限流 | 见 4.3 | T1 约 3–4 小时，T2 约 3–4 小时 |

### 主检验（正式预注册时细化）

- **问题 1：** pair+LLM 相对 pair+oracle 的保留率。
- **问题 2：** pair+LLM vs 逐条打分，以及 vs rubric，在金标准上的差别（Holm 校正）。
- **问题 3（T2）：** pair+LLM vs PPO+手写奖励，在金标准、踩花坛次数、成功率上的差别。

## 6. 主要风险

1. **裁判太弱。** 校准阶段如果达不到 go 判据，先改摘要格式；仍不行就升级到 Sonnet，即方案 C 的成本量级。
2. **摘要本身"泄露"了奖励。** T1 只给原始物理量和事件，不给奖励分项，并用附录消融确认。T2 本身就是事件序列，这一点要在论文里说明。
3. **T2 被视为玩具任务。** 如实写进局限，把真实 LLM agent 任务列为后续。
4. **L=50 不成立。** 第 0 阶段用免费的 oracle 实验先验证。
5. **花费超支。** 客户端设每次运行的花费上限，超了就停，并写日志。
