# LLM 智能体实验：设计说明（2026-11-01）

检验的具体判据在 `prereg.md`；这里写为什么这样设计、花多少钱、怎么跑。

## 1. 要补的缺口

论文现在只有小 MLP 加经典控制任务，LLM 裁判只做了校准和一个 5 种子的 LunarLeft 试点。顶会审稿人一定会问两件事：

- **在 LLM 上成立吗？**
- **你的逐步信用分配和 GiGPO 比怎么样？** GiGPO（NeurIPS 2025）是多轮 LLM 智能体逐步信用分配的标准基线。

这个实验对应论文的三条主张：

1. 同粒度下，用比较代替标量回报没有可检测的代价。
2. 只用比较也能做逐步信用分配。
3. 用 LLM 裁判代替手写奖励时，让裁判排名比让它打分更好。之前的校准只测了标签质量，没测训练。

## 2. 环境：为什么主环境是 WebShop，不是 ALFWorld

| | ALFWorld | WebShop |
|---|---|---|
| 训练奖励 | 成功 10 / 失败 0，加无效动作惩罚 | verl-agent 默认也是二值；但环境自带分级的 task score ∈ [0,1] |
| 比较 vs 标量 | 回报几乎二值。轨迹层面比较与"减均值"按构造成比例，**检验不出东西** | 分级分数下比较会丢掉幅度信息，是真检验 |
| 裁判的任务 | 回合只在成功时提前结束，看长度就能猜出成败，"不需要奖励"不成立 | 回合总是以"购买"结束，裁判要判断买的东西是否符合指令，这正是手写公式想近似的东西 |
| 每回合步数 | ≤ 50 | ≤ 15 |
| 单次运行估计 | 约 25 GPU 小时 | 约 12 GPU 小时 |

WebShop 的 task score 是一个手写公式：属性、选项、价格、商品类型逐项匹配后加权。它本身就是"手写奖励"的现成例子，可以把三条主张串成一个故事：

- 公式的**幅度**需要吗？（E1）
- 公式能被裁判**替代**吗？（E2）
- 裁判应该**排名**还是**打分**？（E2）

ALFWorld 作为可选的第二环境（第 6 节第 3 档），用来复现 E1 的主检验。

## 3. 框架与模型

- **框架：** verl-agent（GiGPO 作者的官方实现），固定在提交 `20bd331`（2026-06-09）。它带 GRPO、GiGPO、PPO 等实现，以及 WebShop/ALFWorld 环境。更新的逐步方法 HGPO（ICLR 2026）、GraphGPO（ICML 2026）也在里面，只在相关工作里讨论，不跑。
- **模型：** Qwen2.5-1.5B-Instruct，和 GiGPO 论文表格一致，有公布数字可以对照。7B 每次运行要 4 张 H100，成本翻 4 倍，不做。
- **超参：** 全部沿用 `examples/gigpo_trainer/run_webshop.sh`。只改不影响数学的设置：1 张 GPU、TP=1、显存比例、micro-batch。
- **新增代码**以补丁形式放在本目录，打在固定提交上：
  - `pair_adv.py`：比较式优势估计。
  - 裁判调用。
  - 比较 critic。
  - 训练器里的少量分派代码。

## 4. 比较式估计器的定义原则

每个比较臂和对应的标量方法用**同一个量、同一个分组**，唯一的差别是：

- 标量："组内减均值（除以标准差）"
- 比较："组内与其他每个样本比较，取符号的平均"

即 A_i = mean_{j≠i} sign(x_i − x_j)，也就是中心化的秩。这样"同粒度"在代码层面是字面意义上的同粒度。比较臂最后把整批优势除以标准差（只缩放），与 MLP 实验的 `phase_b.py` 相同。详细定义见 `prereg.md`。

## 5. 裁判

- **本地开源模型，用 vLLM 和训练进程共用同一张 H100**（裁判约占 22% 显存）。不花 API 钱，也没有速率限制。
- **裁判只看环境给出的文字：** 指令，加购买的商品页（标题、价格、所选选项、描述）。它看不到分数，也看不到智能体自己写的任何文字，所以策略没法用话术"说服"裁判。
- **校准在训练前做**，覆盖训练早、中、晚三个阶段裁判实际会面对的比较。这是 LunarLeft 试点的教训：v1 只校准了最终要区分的那种比较，训练早期的比较没覆盖到。
- **候选裁判**按 Qwen3-8B → 14B → 32B（FP8）的顺序，选第一个过门槛的。

## 6. 算力与费用

**价格：** AWS 价目表 API（us-east-1，按需），ml.p5.4xlarge（1 张 H100 80GB，16 vCPU，256 GiB 内存）在 SageMaker Studio 上的价格是 **$7.912/小时**。每个运行占一个这样的实例。

**单次运行时长（估计，不确定性大）：**

- GiGPO 论文给的 ALFWorld 1.5B 每次迭代约 363 秒，用的是 2 张 H100。
- 按 1 张卡、WebShop 的回合更短来折算，WebShop 一次运行约 12 小时、约 $100；ALFWorld 约 25 小时、约 $200。
- 误差可能在 ±40%。Phase 0 实测后重新估算，再决定跑哪几档。

| 档 | 内容 | 运行数 | 估计费用 |
|---|---|---|---|
| Phase 0 | 环境搭建与调试（约 40 小时）；按公布设置复现 GiGPO、GRPO 各 1 种子；裁判校准 | 2 + 校准 | 约 $600–900 |
| 1 核心 | E1 主检验（gigpo 8、pair_gigpo 8、pair_grpo 5）+ E2 主检验（J-rank 8、J-score 8） | 37 | 约 $3,700 |
| 2 扩展 | pair_step 5、pcrit_res 5（论文自己的逐步方法）；J-score-pair 5；grpo 3 | 18 | 约 $1,800 |
| 3 可选 | ALFWorld 复现 E1 主检验（gigpo 8、pair_gigpo 8、pair_grpo 5） | 21 | 约 $4,200 |

**推荐 Phase 0 + 第 1、2 档，约 $6,300（±40%）。** 裁判臂每次运行多约 20% 的时间，已经算进误差里。 第 3 档等 WebShop 结果和时间再定。

**并行：** 同时开约 16 个实例，第 1、2 档约 4 轮 × 13 小时，大约 3 天跑完。

## 7. 基础设施

- **每个运行一个单卡 H100 实例**（SageMaker Studio 空间），通过 SSH 启动并取回结果。
- **云环境的具体情况**（额度、网络、空闲关机、镜像）记在本地未跟踪的 `llm/infra_local.md` 里。账号 ID、ARN、域 ID、空间名都不进这个公开仓库。
- **结果：** 每个运行的日志、验证曲线和最终评测都拉回本仓库 `llm/results/`。检查点只留在实例上，不进 git。

## 9. 主要风险

1. **复现不了公布数字：** 按门槛停下来查，不跑任何比较臂（"先复现厂商公布的数字"）。
2. **1 张卡显存不够：** 参考模型放 CPU（脚本已经这样做）、调 micro-batch，裁判和训练共用显存需要调比例。
3. **WebShop 环境依赖：** Java 和 pyserini 在 Studio 镜像上可能要额外装。
4. **结论不稳：** 种子数按 `prereg.md` 的功效估计定（主检验 8 个），Phase 0 的单种子只用来过门槛，不下任何结论。
5. **裁判与公式不一致：** 裁判有合理的理由和公式意见不同时（例如公式对字面匹配过于严格），公式当金标准会低估裁判。这点在 4.15b 已经见过。评测同时报告成功率和独立评审（可选，用剩下的约 $10 Gemini 额度）。
